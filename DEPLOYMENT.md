# Deploy Restrictapp on Render + Neon

One Render Python web service serves both the frontend and FastAPI. Neon stores accounts, profiles, sessions, saved trips, checklist progress, and login-rate counters. The compressed travel reference stays in the Git repository. SQLite remains the default for local development.

## 1. Create the Neon database

1. Sign in at [Neon](https://console.neon.tech/) and create a project named `restrictapp` on the Free plan.
2. Choose a European region near Render Frankfurt if available. Keep the initial database (`neondb`) and role, or use your own dedicated role/database.
3. Open **Connect**. Select the database and role, enable connection pooling, and copy the PostgreSQL connection string. Preserve its `sslmode=require` and `channel_binding=require` parameters.
4. Keep that string private. It includes a database password. Paste it into Render's environment-variable form, not Git, screenshots, or this chat.

The app creates its tables during startup, so its role needs permission to create tables in the database. No Oracle, MongoDB, or separate Neon Auth service is needed. See [Neon's Python connection guide](https://neon.com/docs/guides/python).

## 2. Upload the prepared code to GitHub

The deployment preparation is local until committed and pushed. Review the changes first. In this repository, upload the new application, tests, deployment files, requirements, import/migration scripts, and `api/reference_data/`, including its licence and notice. The ignored `api/data/`, `.venv/`, and `.env` must remain excluded.

From the repository root, after reviewing:

```powershell
git status --short
git add .gitignore .env.example render.yaml requirements.txt requirements-lock.txt README.md DEPLOYMENT.md SOURCE_EVALUATION.md api/main.py api/storage.py api/security.py api/legacy_main.py api/countries.json api/planning.py api/guidance.py api/entry_reference.py api/travel_data.py api/static/app api/reference_data scripts tests
git diff --cached --stat
git commit -m "Prepare Restrictapp for Render and Neon"
git push
```

The existing repository is https://github.com/albertolzui/restrictapp. Keep the branch you intend to deploy selected in Render; pushing to another branch will not update it automatically.

## 3. Create the Render service

1. Sign in at [Render](https://dashboard.render.com/), connect GitHub, and allow access to the Restrictapp repository.
2. Choose **New → Blueprint**, select the repository and deployment branch, and let Render read the root `render.yaml`.
3. Supply the private Neon connection string when prompted for `DATABASE_URL`.
4. Confirm the single service uses the **Free** plan, then deploy.

The Blueprint does not create a Render database or a paid disk. It configures:

| Setting | Value |
| --- | --- |
| Runtime | Python 3.12.12 |
| Region | Frankfurt |
| Build | `pip install -r requirements-lock.txt` |
| Start | `python -m uvicorn api.main:app --host 0.0.0.0 --port $PORT --proxy-headers --forwarded-allow-ips='*'` |
| Health check | `/api/health` |
| `RESTRICTAPP_ENV` | `production` |
| `RESTRICTAPP_SECURE_COOKIES` | `1` |
| `RESTRICTAPP_RATE_SECRET` | Random value generated by the Blueprint |
| `DATABASE_URL` | Your private Neon connection string |

If using **New → Web Service** instead of Blueprint, enter these settings manually, leave **Root Directory** empty, choose Free, and generate a random rate secret of at least 32 characters. Render's edge handles HTTPS; the proxy flags are intended for this hosted environment.

Render supplies `RENDER_EXTERNAL_HOSTNAME`, which the app uses to validate the Host header. When adding a custom domain, set `RESTRICTAPP_ALLOWED_HOSTS` to both the original Render hostname and the custom hostname, comma-separated without schemes or paths.

See [Render's FastAPI deployment guide](https://render.com/docs/deploy-fastapi) and [Blueprint reference](https://render.com/docs/blueprint-spec).

## 4. Optional: migrate the existing local records

Skip this step if you want a fresh database. This migrates only the current Restrictapp 2 SQLite database, not the original MongoDB database. Plaintext passwords are rejected. Password hashes, profiles, saved trips, and checklist checks are copied; sessions are omitted so users sign in again.

Run the migration before people register on the deployed app. The target must contain no users, trips, profiles, checklist records, or sessions. It never merges or overwrites an existing user database.

First inspect locally; this does not connect to Neon or change any records:

```powershell
.\.venv\Scripts\python.exe -m scripts.migrate_sqlite --source api/data/restrictapp.sqlite3
```

Make a backup before transferring data. For a live SQLite database, Python's backup API provides a consistent copy:

```powershell
.\.venv\Scripts\python.exe -c "import sqlite3; src=sqlite3.connect('api/data/restrictapp.sqlite3'); dst=sqlite3.connect('api/data/pre-neon-backup.sqlite3'); src.backup(dst); dst.close(); src.close()"
```

Set the Neon URL only in the terminal process, using a masked prompt so it isn't written into a command or shell history. Prefer Neon’s **direct** connection string for this one-time migration:

```powershell
$neonConnection = Read-Host 'Paste the private Neon connection string' -AsSecureString
$env:DATABASE_URL = [System.Net.NetworkCredential]::new('', $neonConnection).Password
.\.venv\Scripts\python.exe -m scripts.migrate_sqlite --source api/data/pre-neon-backup.sqlite3 --apply
Remove-Item Env:DATABASE_URL
```

The transfer commits as one transaction and checks row counts. On a data-copy failure, imported rows are rolled back. Schema creation may already have completed. The source database is read-only and is not deleted. A second successful import into the same populated destination is refused.

## 5. Verify the deployment

Open the HTTPS `onrender.com` URL from Render. `/api/health` should return `status: ok` and `database: postgresql`.

Create a test account, save a traveler profile and trip, tick a checklist item, sign out, and sign in again. Then manually restart the Render service and confirm that the saved data is still present. Check a tourism reference and a study/work links-only result, and try official guidance. These checks exercise the actual Neon connection and Render's HTTPS proxy.

Login/signup protection allows up to 10 submissions per email and 60 per client IP in each 15-minute window, including successful submissions. A rejected request returns HTTP 429 with `Retry-After`. Tests should use separate test addresses and avoid repeatedly registering/signing in against a real user account.

## Operations and limits

- Render Free sleeps after inactivity and has an ephemeral filesystem. Never put the production SQLite database there. Neon is the durable account store; keep database backups outside this repository. [Render Free limits](https://render.com/docs/free), [Neon pricing](https://neon.com/pricing).
- Deployments install the bundled reference snapshot. Its dates age even while the app sleeps; the app withholds old categories. Use `SOURCE_EVALUATION.md` to review and refresh it before committing an update. No automatic data-update job is installed.
- No password-reset or email-verification flow is included yet. This is an initial public beta, not a complete account-management product.
- Custom domain registration is separate from free hosting. The Render HTTPS subdomain is enough for initial testing.
- Production startup fails if `DATABASE_URL`, secure-cookie settings, TLS, or the rate secret are missing. Database health failures return HTTP 503 without credentials.
- If signup returns `Invalid origin`, verify HTTPS/proxy start flags and the deployed hostname. If startup cannot connect, confirm the Neon role, password, database, TLS query parameters, and active project.
- Rollback: redeploy a previous compatible app commit. Local SQLite is retained unless you explicitly remove it; the cloud migration does not switch or erase your local development database.

## Optional local PostgreSQL integration test

The integration suite only permits a disposable local database named `restrictapp_test`. It refuses remote hosts and other database names. With Docker running:

```powershell
docker run --rm -d --name restrictapp-postgres-test -e POSTGRES_DB=restrictapp_test -e POSTGRES_PASSWORD=local-test-only -p 127.0.0.1:55432:5432 postgres:17-alpine
$env:RESTRICTAPP_TEST_DATABASE_URL = 'postgresql://postgres:local-test-only@127.0.0.1:55432/restrictapp_test'
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
Remove-Item Env:RESTRICTAPP_TEST_DATABASE_URL
docker stop restrictapp-postgres-test
```

This temporary database is disposable; don't substitute a real database into this test command.
